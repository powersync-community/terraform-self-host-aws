# Database

This guide is for whoever runs and operates the Postgres database behind this deployment. It covers the layout Terraform builds, the logical replication PowerSync depends on, the least-privilege roles, the one-time bootstrap, the network posture, how to verify replication, what to change for production, and how to migrate the source database later.

The infrastructure lives in [`../infra/README.md`](../infra/README.md); the bootstrap and seed tooling lives in [`../example-client/README.md`](../example-client/README.md).

## One instance, two databases

Terraform provisions a single Amazon RDS for PostgreSQL instance (`infra/modules/rds/main.tf`) and puts two databases on it:

- `app`: the source application database. It holds your business tables (the demo ships a single `lists` table).
- `powersync`: PowerSync's bucket storage. This is where the service persists the sync buckets it builds from the source.

The two database names come from `infra/locals.tf` (`source_db = "app"`, `storage_db = "powersync"`). Terraform creates the `app` database directly on the instance (`db_name`). The `powersync` database is created during bootstrap (see below).

Running the source and the bucket storage on one instance keeps the demo cheap and simple. Postgres 14 and later support the separate-databases layout used here. The tradeoff is CPU: the replicator reading from `app` and the storage writes into `powersync` share the same instance, so under load they compete. For production, split them onto separate instances so each scales on its own and a heavy replication backlog cannot starve client reads.

The connection URIs are assembled in `infra/locals.tf` (`source_uri`, `storage_uri`) from the host, port, role names, and generated passwords, then rendered into `infra/config/service.yaml.tftpl` and stored in the config secret. Both URIs carry `sslmode=verify-full`, which validates the RDS server certificate against the AWS RDS CA that ships inside the PowerSync service image, so no separate CA file is needed. If you front the database with a private CA instead, switch to `sslmode=verify-ca` and add a `cacert` with the certificate in PEM form.

## Logical replication

PowerSync's replicator consumes Postgres logical replication. Two things have to be in place.

1. The instance-level setting `rds.logical_replication = 1`. Terraform sets this in the DB parameter group (`infra/modules/rds/main.tf`). It is a static parameter, so it applies on boot; a freshly created instance comes up with it already enabled. Changing it later on an existing instance requires a reboot.
2. A publication named `powersync`. Bootstrap creates it with `CREATE PUBLICATION powersync FOR ALL TABLES`, which also covers tables you add later. PowerSync replicates from this publication.

## The two least-privilege roles

PowerSync connects with two roles, each scoped to the least it needs. Their passwords are generated by Terraform (`infra/database.tf`, `random_password` with `special = false` so the values stay alphanumeric and need no URL-encoding in the connection URIs).

**`powersync_source`** reads the source database for replication. It is read-only. Bootstrap grants it:

- `rds_replication` (the RDS role that permits logical replication)
- `CONNECT` on the `app` database
- `USAGE` on schema `public`
- `SELECT` on all current tables in `public`
- `SELECT` by default on future tables in `public` (via `ALTER DEFAULT PRIVILEGES`)

It never gets write privileges. It reads rows and consumes the replication stream, nothing more.

**`powersync_storage`** owns the `powersync` bucket-storage database (`CREATE DATABASE powersync OWNER powersync_storage`). Ownership lets PowerSync create and manage its own storage schema inside that database. This role has no rights on the source database.

On Postgres the API tasks and the replication tasks use the same storage role, so the api config is identical to the main config (`config_api_b64 = config_b64` in `infra/locals.tf`). The separate api-config secret exists to keep the two-secret plumbing in place for other backends.

## One-time bootstrap

Terraform provisions the instance and the `app` database, but it does not run SQL. Creating the roles, the publication, and the storage database is a one-time step run from the example client:

```
cd example-client
npm run bootstrap
```

The script (`example-client/bootstrap-db.ts`) reads everything from Terraform outputs: the endpoint, the master credentials, and the two generated role passwords. It connects as the RDS master user with the `pg` driver and, in order, creates or updates the two roles, applies the source-read grants, creates the `powersync` publication if absent, and creates the `powersync` database owned by the storage role if absent.

To reach the database from your workstation, the script wraps its work in a temporary RDS security-group allowlist (`withTempAccess`): it authorizes your public IP on port 5432, does the work, then revokes it. This is the same mechanism the seed scripts use.

Every step is guarded (`IF NOT EXISTS` / existence checks before create), so the bootstrap is idempotent and safe to re-run.

Run bootstrap once after `terraform apply`, before seeding or starting to sync. After it, `npm run seed` loads demo data.

## Network access posture

The database listens on 5432. A security group is the gate (`infra/modules/rds/main.tf`):

- The ECS tasks' security group is always allowed in.
- Any CIDRs in `var.admin_cidr` are allowed in (for example your workstation, for bootstrap and seeding). This ingress rule is only created when `admin_cidr` is non-empty.

For demo convenience the instance is `publicly_accessible = true` and sits in public subnets, which is what lets the example client reach it from a laptop. The security group, not the public flag, is the actual access control.

To make the database private for production:

- Move it to private subnets (pass private subnet IDs to the module's `subnet_ids`).
- Set `publicly_accessible = false`.
- Reach it for admin work through a bastion host or AWS Systems Manager Session Manager (SSM) port forwarding rather than a public IP allowlist. The ECS tasks stay inside the VPC, so they are unaffected.

## Verify replication

After bootstrap, seeding, and the first sync, confirm the replication slot exists and is active. Connect to the `app` database and run:

```sql
SELECT slot_name, active, wal_status
FROM pg_replication_slots;
```

You want a row for the PowerSync slot with `active = true` and a healthy `wal_status` (`reserved`, not `lost`).

PowerSync also exposes a diagnostics endpoint that reports replication health from the service's side. The fields to watch:

- `slot active`: the logical replication slot is connected and consuming.
- `initial_replication_done`: the first full copy of the source has finished; incremental streaming has taken over.
- `replication_lag_bytes`: how far the slot is behind the source's write-ahead log. A steadily growing value means the replicator is not keeping up.
- `wal_status`: the slot's WAL retention state, mirroring the Postgres column above.

## Production hardening

The RDS module is tuned for a demo. For production, change these (`infra/modules/rds/main.tf`):

- **Private networking.** Private subnets and `publicly_accessible = false` (see above).
- **Multi-AZ.** Enable a standby in a second Availability Zone for failover.
- **Backups.** `backup_retention_period` is `1` day here; raise it. `skip_final_snapshot = true` means teardown discards the data; set it `false` so a destroy takes a final snapshot.
- **Deletion protection.** `deletion_protection = false` here; set it `true` so the instance cannot be deleted by accident.

Storage is already encrypted (`storage_encrypted = true`) and uses `gp3`.

## Migrating the source database

You can move the source database to a new Postgres server later (a bigger instance, a split-out source, a different provider). Point PowerSync's source connection at the new host.

Because logical replication slots are tied to a specific server, the new server starts with a fresh slot. PowerSync detects this and re-runs initial replication: it copies the source in full, rebuilds its buckets, and clients re-download the data once. This happens in the background with no downtime for connected clients.

Several prerequisites do not travel inside a `pg_dump`, so set them up on the new server before you cut over:

- `wal_level` / `rds.logical_replication` enabled (on RDS, the parameter-group setting; on self-managed Postgres, `wal_level = logical`).
- The `powersync` publication.
- The `powersync_source` role and its grants.

A dump restores your tables and data, not the replication configuration or the roles, so recreate those with the same bootstrap steps described above.

See [`auth.md`](auth.md) for the token side of a migration: the client audience derives from the deployment domain, so tokens stay valid across a source-database move.
