# MongoDB Atlas cluster module

This module is an alternative data layer for the self-hosted PowerSync deployment. The default
deployment runs on Amazon RDS Postgres (`modules/rds`). This module provisions a MongoDB Atlas
cluster in its place, reachable from the ECS tasks over AWS PrivateLink.

The code here is real and complete, but it is wired in only from a commented example in
`../../main.tf` (the "OPTIONAL: MongoDB Atlas instead of RDS" section). Nothing here runs until
you uncomment that path. Read this guide if you are deciding between RDS and Atlas for the source
and bucket-storage databases.

For the rest of the infrastructure, see the [main infra guide](../../README.md).

## What this module provisions

One instance of this module provisions a cluster, its database users, and (optionally) the
PrivateLink chain that reaches it.

### The cluster

`mongodbatlas_advanced_cluster.this` is a single-region replica set on AWS:

- `cluster_type = "REPLICASET"` with `node_count = 3`, the standard Atlas electable layout and the
  only one M10 offers. `priority = 7` marks the single region as primary.
- `instance_size` defaults to `M10`. That is the floor for AWS PrivateLink; M0 and shared tiers
  cannot use private endpoints.
- `region_name` defaults to `US_EAST_1` (Atlas spelling). Match it to the AWS VPC region so the
  PrivateLink endpoint stays single-region.
- `mongo_db_major_version` defaults to `null`, which lets Atlas pick the current default version.

The module targets the mongodb/mongodbatlas provider `~> 2.0`, whose schema expresses
`replication_specs`, `region_configs`, and `electable_specs` as list-of-object attributes rather
than nested blocks.

### Database users

The module creates three SCRAM users, each scoped to exactly what one PowerSync process touches.
Every password is generated by a `random_password` (length 32, `special = false` to avoid
URL-encoding in the connection strings) and is never committed. Usernames are prefixed with
`db_username` (default `powersync`):

- **Source user** (`<db_username>_source`): `readWrite` on `source_database` (default `db`). Covers
  the source application data plus the connector's `_powersync_checkpoints`.
- **Storage full user** (`<db_username>_full`): `readWrite` on `storage_database` (default
  `buckets`). Used by the replication and compact processes that own bucket storage.
- **Storage API user** (`<db_username>_api`): a least-privilege user for the client-facing API
  process. It is granted a custom project-scoped role (`api_role_name`, default
  `powersyncApiStorage`) that allows `FIND` and `LIST_COLLECTIONS` across the storage database,
  `INSERT` and `UPDATE` limited to the `write_checkpoints` and `connection_report_events`
  collections, and `REMOVE` limited to `connection_report_events`. The role has no
  `createCollection` action, so those two collections must already exist (created by the
  full-access replicator or a migration) before this user writes to them. Custom roles are
  assigned from the `admin` database.

This split is the reason the Atlas path uses two config secrets. On Postgres the API and the
replicator share one storage role, so the two secrets are identical (see `locals.tf`). On Atlas
the API secret carries the stricter storage-API user while the replicator secret carries the full
user.

### PrivateLink chain

When `create_private_endpoint = true` (the default), the module stands up the full chain that lets
the ECS tasks reach the cluster privately, with Terraform ordering the three steps:

1. `mongodbatlas_privatelink_endpoint.this`: Atlas allocates a PrivateLink endpoint service and
   returns its service name.
2. `aws_vpc_endpoint.atlas`: an AWS interface endpoint created from that service name, placed in
   `private_subnet_ids` with `endpoint_sg_id` attached. `private_dns_enabled = false`, because the
   standard `mongodb+srv` host does not resolve here.
3. `mongodbatlas_privatelink_endpoint_service.this`: hands the AWS endpoint id back to Atlas. This
   is the link-back that replaces the manual "approve in Atlas" step.

A `mongodbatlas_advanced_cluster` data source re-reads the cluster after the endpoint service is
live, with a `depends_on` on step 3. The cluster resource captures its connection strings at
create time, before any endpoint exists, so reading from the resource would leave the
private-endpoint string empty on a fresh apply. Reading from the data source populates the `-pri`
connection string within a single `terraform apply`.

The `private_endpoint_srv` output selects the correct `-pri` string by matching on the interface
endpoint id, since a cluster can list several private-endpoint hosts (one per registered or stale
endpoint) and picking the wrong one resolves to an endpoint outside this VPC. Other outputs include
`standard_srv` (public DNS, usable only with an IP access-list entry), the three usernames and
their passwords (all sensitive), `vpc_endpoint_id`, and `vpc_endpoint_dns`.

## The two-cluster pattern

The example in `../../main.tf` instantiates the module twice, so the source data and the bucket
storage live on separate clusters while sharing one regional PrivateLink endpoint:

- **`module.atlas`** is the source cluster. It uses the defaults, so `create_private_endpoint`
  stays `true` and it creates the PrivateLink chain for the region.
- **`module.atlas_storage`** is the bucket-storage cluster (`instance_size = "M10"`,
  `name_prefix = "${local.name_prefix}-storage"`). It sets `create_private_endpoint = false` and
  passes `existing_vpc_endpoint_id = module.atlas.vpc_endpoint_id`, so it reuses the single regional
  endpoint instead of creating a second one. Its cluster is already attached to that regional
  endpoint by Atlas, so its own `-pri` string resolves against the reused endpoint id.

If you run two clusters in the same Atlas project, give the second instance a distinct
`api_role_name`. The custom API storage role is project-scoped, so two instances that both use the
default name collide (see the variable's own description in `variables.tf`).

## Switching from RDS to Atlas

The steps below are the ones spelled out in the commented section of `../../main.tf`. This module
is code only; it does not modify the deployment until you make these edits.

1. Uncomment the `mongodbatlas` provider block in `providers.tf`, its `required_providers` entry in
   `versions.tf`, and the `atlas_*` variables in `variables.tf`.
2. Uncomment the two module blocks (`module.atlas` and `module.atlas_storage`) in `main.tf`, remove
   the `module.rds` block above them, and rewire the Postgres locals in `locals.tf` so the
   `source_uri` and `storage_uri` are built from the Atlas `mongodb+srv` connection strings instead
   of the Postgres URIs (the git history holds the shape these locals took). The source URI carries
   the `/db` path, the storage URI the `/buckets` path.
3. Re-add the Atlas PrivateLink security group to `modules/network` and expose it as
   `atlas_endpoint_sg_id`, which the module blocks pass in as `endpoint_sg_id`. This security group
   accepts the MongoDB port range from the ECS tasks.

## Credentials

Authenticate the provider with a project-scoped Atlas Service Account (OAuth2). The Service Account
must hold Project Owner on the target project. Supply three values as `TF_VAR_*` environment
variables, matching the sensitive `atlas_*` variables you uncomment in `variables.tf`:

- `TF_VAR_atlas_client_id`: the Service Account client id.
- `TF_VAR_atlas_client_secret`: the Service Account client secret.
- `TF_VAR_atlas_project_id`: the Atlas project id the cluster is created in.

The provider block reads `client_id` and `client_secret`; the module reads `project_id` as
`var.atlas_project_id`.

## Caveat: one PrivateLink service per region per project

This is the difference that matters most when comparing Atlas to RDS. Atlas permits only one
PrivateLink endpoint service per region per project, and a cluster's private endpoint is shared
across every cluster in that region and project. So the `deployment_name` prefix does not give you
isolated multi-deployment on Atlas the way it does on RDS. Two Atlas-backed deployments in the same
Atlas project and region cannot each stand up their own private endpoint. If you need them side by
side, give each deployment its own Atlas project or its own region. RDS has no such limit, which is
why it is the default data layer in this repo.
